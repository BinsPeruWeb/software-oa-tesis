MODELO DE DATOS — PLATAFORMA OA
================================

1. IDEA GENERAL
---------------

La base de datos organiza la información siguiendo este recorrido:

Usuario médico
  -> Paciente
     -> Episodio clínico
        -> Radiografía
           -> Rodilla analizada
              -> Predicción y Grad-CAM
                 -> Revisión médica
                    -> Reporte PDF

También guarda las sesiones, antecedentes, datos clínicos, configuraciones y
eventos de auditoría del sistema.


2. USUARIOS Y ACCESO
--------------------

roles
  Define los dos tipos de usuario disponibles:
  - ADMIN: administrador técnico.
  - CLINICIAN: médico.

users
  Guarda las cuentas de acceso: nombre, correo, contraseña cifrada mediante
  hash y rol. Para los médicos también conserva DNI cifrado, CMP y
  establecimiento de salud.

mfa_credentials
  Guarda la configuración de autenticación en dos pasos de cada usuario.

sessions
  Representa las sesiones iniciadas. Permite conocer cuándo vencen o fueron
  cerradas.

Relación principal:
  Un rol puede pertenecer a muchos usuarios.
  Un usuario puede tener una configuración MFA y varias sesiones.


3. PACIENTES E HISTORIA CLÍNICA
-------------------------------

patients
  Contiene la identidad principal del paciente: historia clínica, DNI,
  nombres, apellidos, nacimiento y sexo.

  Cada paciente pertenece a un único médico responsable. Los datos sensibles
  se almacenan cifrados. El DNI y la historia clínica también tienen un índice
  HMAC que permite buscarlos sin guardarlos como texto visible.

patient_contacts
  Guarda el teléfono y correo del paciente, ambos relacionados directamente
  con su ficha.

patient_clinical_profiles
  Guarda el estado clínico actual:
  - dolor de 0 a 10;
  - obesidad;
  - diabetes;
  - hipertensión;
  - consumo de nicotina;
  - trauma de miembro inferior.

prior_exams
  Guarda exámenes antiguos que no fueron realizados dentro del sistema.
  Incluye fecha, rodilla, KL confirmado y datos clínicos históricos. Estos
  antecedentes se utilizan para los análisis longitudinales.

Relación principal:
  Un médico puede registrar muchos pacientes.
  Un paciente tiene un contacto, un perfil clínico y varios antecedentes.


4. EPISODIOS Y RADIOGRAFÍAS
---------------------------

clinical_episodes
  Agrupa todo lo realizado en una fecha de atención o análisis. Un paciente
  puede tener varios episodios a lo largo del tiempo.

stored_assets
  Registra la ubicación de los archivos cifrados:
  - radiografías;
  - imágenes Grad-CAM;
  - reportes PDF.

  La tabla no contiene directamente el archivo. Guarda su ruta interna, tipo,
  tamaño y hash para comprobar su integridad.

image_preflight_reviews
  Guarda el resultado de la revisión visual previa realizada antes de aceptar
  una imagen. Indica si corresponde a una radiografía de rodilla y si parece
  bilateral o de una sola rodilla.

radiographic_studies
  Representa la radiografía cargada. Guarda la fecha, formato detectado,
  opciones de orientación, archivo asociado y revisión visual previa.

knee_observations
  Indica qué rodilla de la radiografía será analizada:
  - L: izquierda.
  - R: derecha.

Relación principal:
  Un paciente puede tener muchos episodios.
  Un episodio puede contener uno o más estudios.
  Cada estudio apunta a una radiografía cifrada y genera una observación de
  rodilla.


5. PROCESAMIENTO Y MODELOS DE INTELIGENCIA ARTIFICIAL
-----------------------------------------------------

inference_jobs
  Funciona como una cola de trabajos. Guarda qué análisis debe ejecutarse y su
  estado:
  - QUEUED: en espera.
  - RUNNING: ejecutándose.
  - SUCCEEDED: terminado correctamente.
  - FAILED: no pudo terminar.

  La clave de idempotencia evita crear el mismo trabajo más de una vez.

model_predictions
  Guarda los resultados producidos por los modelos:
  - modelo y versión;
  - probabilidades;
  - KL estimado;
  - riesgo calculado;
  - umbral usado;
  - hashes de los modelos y de la entrada;
  - dispositivo y tiempo de procesamiento.

  Esta tabla puede almacenar resultados del ensemble CNN, XGBoost o LSTM.

gradcam_explanations
  Relaciona una predicción con los mapas Grad-CAM de ResNet50 y DenseNet121.
  Cada mapa se guarda como un archivo cifrado.

clinical_observations
  Conserva una copia de los datos clínicos que tenía el paciente al momento
  exacto del estudio. Así, si su perfil cambia después, el análisis original
  continúa teniendo su contexto histórico.

Relación principal:
  Una observación de rodilla puede generar varios trabajos.
  Cada trabajo terminado puede producir una predicción.
  Una predicción KL puede tener dos mapas Grad-CAM.


6. REVISIÓN MÉDICA Y REPORTES
-----------------------------

clinician_reviews
  Guarda la decisión del médico sobre una predicción KL:
  - CONFIRMED: confirmó el resultado.
  - CORRECTED: cambió el grado KL.
  - REJECTED: rechazó la predicción.

  También registra quién revisó y cuándo lo hizo. La predicción original no se
  modifica, por lo que se mantiene la trazabilidad.

draft_reports
  Registra los PDF generados. Hay dos tipos:
  - EPISODE: contiene un episodio específico.
  - LONGITUDINAL: reúne la evolución del paciente.

  El PDF real está cifrado y referenciado mediante stored_assets.

Relación principal:
  Una predicción puede recibir revisiones médicas.
  Un episodio puede generar varios reportes en fechas diferentes.


7. CONFIGURACIÓN Y AUDITORÍA
----------------------------

app_settings
  Guarda configuraciones generales, como el nombre de la institución, el
  subtítulo del reporte y el prefijo de historia clínica.

audit_events
  Registra acciones importantes: inicios de sesión, cambios, análisis,
  revisiones y descargas. Incluye actor, acción, entidad, fecha y datos de
  contexto.

  Es una tabla de solo agregado: PostgreSQL impide editar o eliminar sus
  registros.

schema_migrations
  Lleva el control de las migraciones SQL que ya fueron aplicadas para no
  ejecutarlas nuevamente.


8. EJEMPLO RÁPIDO
-----------------

1. Un médico se encuentra registrado en users.
2. El médico crea un paciente en patients.
3. Sus datos de contacto van a patient_contacts y sus datos médicos a
   patient_clinical_profiles.
4. Al cargar una radiografía se crea un clinical_episode.
5. El archivo cifrado se registra en stored_assets.
6. La revisión previa se guarda en image_preflight_reviews.
7. La radiografía se registra en radiographic_studies.
8. La rodilla seleccionada se registra en knee_observations.
9. El análisis automático se controla mediante inference_jobs.
10. Los resultados se guardan en model_predictions.
11. Los mapas explicativos se registran en gradcam_explanations.
12. La confirmación o corrección médica se guarda en clinician_reviews.
13. El PDF se registra en draft_reports y su archivo en stored_assets.
14. Las acciones importantes quedan registradas en audit_events.


9. RESUMEN DE RELACIONES
------------------------

ADMIN/MÉDICO (users)
  -> crea o administra PACIENTES (patients)

PACIENTE
  -> tiene CONTACTO (patient_contacts)
  -> tiene PERFIL CLÍNICO (patient_clinical_profiles)
  -> tiene ANTECEDENTES (prior_exams)
  -> tiene EPISODIOS (clinical_episodes)

EPISODIO
  -> contiene RADIOGRAFÍAS (radiographic_studies)
  -> genera REPORTES (draft_reports)

RADIOGRAFÍA
  -> utiliza un ARCHIVO CIFRADO (stored_assets)
  -> puede tener REVISIÓN VISUAL PREVIA (image_preflight_reviews)
  -> produce una OBSERVACIÓN DE RODILLA (knee_observations)

OBSERVACIÓN DE RODILLA
  -> conserva DATOS CLÍNICOS DEL MOMENTO (clinical_observations)
  -> genera TRABAJOS DE INFERENCIA (inference_jobs)
  -> genera PREDICCIONES (model_predictions)

PREDICCIÓN
  -> puede tener GRAD-CAM (gradcam_explanations)
  -> puede tener REVISIÓN MÉDICA (clinician_reviews)

Todo el recorrido relevante queda registrado en AUDITORÍA (audit_events).


10. TABLAS MAESTRAS Y TABLAS DETALLE
------------------------------------

Una tabla maestra representa el registro principal de un grupo de información.
Una tabla detalle contiene datos que dependen de ese registro principal.

Ejemplo simple:

  patients es la tabla maestra del paciente.
  clinical_episodes es una tabla detalle porque cada episodio pertenece a un
  paciente.

Una misma tabla puede ser detalle en una relación y maestra en la siguiente.
Por ejemplo, clinical_episodes es detalle de patients, pero es maestra de
radiographic_studies.


10.1 MAESTRO: roles
-------------------

Detalle: users
Relación: roles.code -> users.role_code
Cardinalidad: un rol puede tener muchos usuarios (1 a muchos).

roles es un maestro de catálogo. Cada usuario debe pertenecer a uno de los dos
roles existentes: ADMIN o CLINICIAN.


10.2 MAESTRO: users
-------------------

Detalles directos:

- mfa_credentials mediante mfa_credentials.user_id
  Cardinalidad: un usuario puede tener cero o una configuración MFA (1 a 0..1).

- sessions mediante sessions.user_id
  Cardinalidad: un usuario puede tener muchas sesiones (1 a muchos).

- patients mediante patients.owner_clinician_id
  Cardinalidad: un médico puede ser responsable de muchos pacientes
  (1 a muchos), pero cada paciente tiene un solo médico responsable.

users también aparece como referencia en campos como created_by, updated_by,
reviewed_by, recorded_by y generated_by. Esas relaciones indican quién realizó
una acción, pero no convierten necesariamente al registro en un detalle
funcional del usuario.


10.3 MAESTRO PRINCIPAL: patients
--------------------------------

Detalles directos:

- patient_contacts mediante patient_contacts.patient_id
  Cardinalidad: un paciente tiene cero o un registro de contacto (1 a 0..1).

- patient_clinical_profiles mediante patient_clinical_profiles.patient_id
  Cardinalidad: un paciente tiene cero o un perfil clínico actual (1 a 0..1).

- prior_exams mediante prior_exams.patient_id
  Cardinalidad: un paciente puede tener muchos exámenes históricos
  (1 a muchos).

- clinical_episodes mediante clinical_episodes.patient_id
  Cardinalidad: un paciente puede tener muchos episodios (1 a muchos).

- stored_assets mediante stored_assets.patient_id
  Cardinalidad: un paciente puede tener muchos archivos cifrados
  (1 a muchos).

patients es la tabla maestra central del área clínica. Contacto, perfil,
antecedentes, episodios y archivos no tienen sentido funcional sin el paciente
al que pertenecen.


10.4 MAESTRO: clinical_episodes
-------------------------------

Detalles directos:

- radiographic_studies mediante radiographic_studies.episode_id
  Cardinalidad: un episodio puede contener uno o varios estudios
  radiográficos (1 a muchos).

- draft_reports mediante draft_reports.episode_id
  Cardinalidad: un episodio puede generar varios reportes (1 a muchos).

clinical_episodes es detalle de patients y, al mismo tiempo, maestro de los
estudios y reportes generados durante ese episodio.


10.5 MAESTRO: image_preflight_reviews
-------------------------------------

Detalle: radiographic_studies
Relación: image_preflight_reviews.id -> radiographic_studies.preflight_id
Cardinalidad: una revisión previa puede asociarse con uno o varios estudios;
para el estudio esta relación es opcional.

Esta tabla conserva la validación previa de la imagen antes de crear el estudio.


10.6 MAESTRO: stored_assets
---------------------------

Detalles o usos del archivo:

- radiographic_studies mediante radiographic_studies.asset_id;
- gradcam_explanations mediante gradcam_explanations.asset_id;
- draft_reports mediante draft_reports.asset_id.

Cardinalidad física: un archivo registrado puede ser referenciado por uno o
varios registros dependientes (1 a muchos).

stored_assets actúa como maestro técnico de archivos. Describe dónde está el
archivo cifrado y permite que una radiografía, un Grad-CAM o un reporte lo use
sin guardar el contenido binario dentro de esas tablas.


10.7 MAESTRO: radiographic_studies
----------------------------------

Detalle: knee_observations
Relación: radiographic_studies.id -> knee_observations.study_id
Cardinalidad: un estudio puede producir una o más observaciones de rodilla
(1 a muchos).

radiographic_studies es detalle de clinical_episodes y maestro de las rodillas
que se analizan a partir de la imagen.


10.8 MAESTRO: knee_observations
-------------------------------

Detalles directos:

- clinical_observations mediante clinical_observations.knee_observation_id
  Cardinalidad: una observación de rodilla tiene cero o una fotografía de datos
  clínicos (1 a 0..1).

- inference_jobs mediante inference_jobs.observation_id
  Cardinalidad: una observación puede generar muchos trabajos de inferencia
  (1 a muchos).

- model_predictions mediante model_predictions.observation_id
  Cardinalidad: una observación puede tener varias predicciones de modelos
  diferentes (1 a muchos).

knee_observations es detalle de radiographic_studies y maestro de la información
clínica y los resultados calculados para una rodilla específica.


10.9 MAESTRO: inference_jobs
----------------------------

Detalle: model_predictions
Relación: inference_jobs.id -> model_predictions.job_id
Cardinalidad: un trabajo puede producir cero o una predicción asociada
(1 a 0..1), porque job_id es único.

El trabajo existe mientras se encuentra en cola o ejecución. Cuando termina
correctamente, su resultado se conserva en model_predictions.


10.10 MAESTRO: model_predictions
--------------------------------

Detalles directos:

- gradcam_explanations mediante gradcam_explanations.prediction_id
  Cardinalidad: una predicción puede tener varios mapas Grad-CAM
  (1 a muchos; normalmente uno por backbone).

- clinician_reviews mediante clinician_reviews.prediction_id
  Cardinalidad: una predicción puede tener varias revisiones médicas
  registradas en el tiempo (1 a muchos).

model_predictions es detalle de una observación de rodilla y, cuando proviene
de un trabajo, también es detalle de inference_jobs. A su vez, funciona como
maestro de explicaciones y revisiones clínicas.


10.11 TABLAS SIN DETALLE FUNCIONAL PROPIO
-----------------------------------------

- app_settings: maestro independiente de configuraciones del sistema.
- audit_events: detalle histórico global de las acciones realizadas; no tiene
  tablas hijas.
- schema_migrations: tabla técnica independiente para controlar qué migraciones
  ya se ejecutaron.


10.12 RESUMEN MAESTRO -> DETALLE
--------------------------------

  -> sessions

  -> patient_contacts
  -> patient_clinical_profiles

  -> draft_reports

image_preflight_reviews

10.13 QUÉ CONTIENE Y PARA QUÉ SE USA CADA TABLA
------------------------------------------------

A continuación se explica cada tabla que aparece en las relaciones de maestros
y detalles. "Tipo" indica el papel principal que cumple dentro del modelo.


TABLA: roles
Tipo: maestro de catálogo.
Qué contiene:
  El código y la descripción de los roles ADMIN y CLINICIAN.
Para qué se usa:
  Para definir si una cuenta pertenece a un administrador técnico o a un
  médico, y determinar a qué módulos puede acceder.


TABLA: users
Tipo: maestro de usuarios.
Qué contiene:
  Correo de acceso, nombre, hash de contraseña, rol, estado de la cuenta,
  intentos fallidos, bloqueo temporal y fechas de creación y actualización.
  Para los médicos contiene además DNI cifrado, índice HMAC del DNI, número de
  CMP y establecimiento de salud donde trabaja.
Para qué se usa:
  Para autenticar personas, asignar permisos, registrar médicos responsables e
  identificar quién realizó cada operación. Los datos profesionales permiten
  identificar al médico sin usar el campo de especialidad.


TABLA: mfa_credentials
Tipo: detalle de users.
Qué contiene:
  Secreto MFA cifrado, estado de activación y fechas de creación y verificación.
Para qué se usa:
  Para configurar la autenticación mediante código temporal de un usuario.


TABLA: sessions
Tipo: detalle de users.
Qué contiene:
  Usuario propietario, fecha de vencimiento, fecha de revocación, creación y
  última actividad.
Para qué se usa:
  Para mantener una sesión iniciada, controlar su vigencia y cerrarla cuando el
  usuario sale o su cuenta es desactivada.


TABLA: patients
Tipo: maestro principal de pacientes.
Qué contiene:
  Historia clínica, DNI, nombres, apellidos, fecha de nacimiento, sexo, médico
  responsable, creador, estado de archivo y fechas de registro. Los campos de
  identidad están cifrados y los identificadores de búsqueda usan HMAC.
Para qué se usa:
  Para representar la ficha principal del paciente y conectar toda su
  información clínica, radiográfica y longitudinal.


TABLA: patient_contacts
Tipo: detalle de patients.
Qué contiene:
  Teléfono y correo electrónico cifrados.
Para qué se usa:
  Para separar los datos de contacto de la identidad clínica principal del
  paciente.


TABLA: patient_clinical_profiles
Tipo: detalle de patients.
Qué contiene:
  Dolor actual, obesidad, diabetes, hipertensión, consumo de nicotina, trauma de
  miembro inferior, usuario que actualizó y fecha de actualización.
Para qué se usa:
  Para conservar el estado clínico actual del paciente y utilizarlo como base
  al crear un nuevo análisis.


TABLA: prior_exams
Tipo: detalle de patients.
Qué contiene:
  Fecha del examen anterior, lateralidad, KL confirmado, dolor y cinco
  indicadores clínicos históricos.
Para qué se usa:
  Para incorporar antecedentes externos que no fueron analizados en la
  plataforma y utilizarlos en los cálculos longitudinales de XGBoost y LSTM.


TABLA: clinical_episodes
Tipo: detalle de patients y maestro de estudios y reportes.
Qué contiene:
  Paciente, fecha de apertura, estado del episodio, creador y fecha de registro.
Para qué se usa:
  Para agrupar las radiografías, resultados y reportes que pertenecen a una
  misma evaluación clínica.


TABLA: stored_assets
Tipo: maestro técnico de archivos y detalle de patients.
Qué contiene:
  Paciente, tipo de archivo, ubicación interna, tipo MIME, nombre original
  cifrado, hash SHA-256, tamaño, creador y fecha.
Para qué se usa:
  Para localizar y comprobar la integridad de radiografías, Grad-CAM y PDF
  almacenados de forma cifrada, sin guardar archivos grandes en PostgreSQL.


TABLA: image_preflight_reviews
Tipo: maestro de validaciones previas de imagen.
Qué contiene:
  Hash de la entrada, clase de archivo, tipo MIME, estado de validación, diseño
  sugerido, compatibilidad, modelo proveedor, identificador de solicitud,
  costo, evaluación, creador y vencimiento.
Para qué se usa:
  Para registrar la revisión que determina si el archivo corresponde a una
  radiografía de rodilla y si contiene una o dos rodillas antes de crear el
  estudio.


TABLA: radiographic_studies
Tipo: detalle de clinical_episodes y maestro de observaciones de rodilla.
Qué contiene:
  Episodio, radiografía cifrada, revisión previa, fecha del examen, formato de
  entrada, confirmaciones técnicas, inversión de polaridad, corrección
  horizontal, creador y fecha.
Para qué se usa:
  Para representar el estudio radiográfico cargado y conservar exactamente las
  condiciones con las que será procesado.


TABLA: knee_observations
Tipo: detalle de radiographic_studies y maestro del análisis de una rodilla.
Qué contiene:
  Estudio de origen y lateralidad izquierda o derecha.
Para qué se usa:
  Para separar el estudio completo de la rodilla específica que se analiza y
  relacionarla con datos clínicos, trabajos y predicciones.


TABLA: clinical_observations
Tipo: detalle de knee_observations.
Qué contiene:
  Dolor, obesidad, diabetes, hipertensión, nicotina, trauma, usuario y fecha del
  registro.
Para qué se usa:
  Para guardar una fotografía de los datos clínicos que tenía el paciente al
  momento del estudio, aunque su perfil actual cambie después.


TABLA: inference_jobs
Tipo: detalle de knee_observations y maestro de una predicción ejecutada.
Qué contiene:
  Observación de rodilla, tipo de trabajo, estado, clave de idempotencia,
  número de intentos, error, correlation ID, creador y tiempos de ejecución.
Para qué se usa:
  Para administrar la cola de análisis KL y Grad-CAM, evitar duplicados y
  recuperar trabajos después de reiniciar los servicios.


TABLA: model_predictions
Tipo: detalle de knee_observations e inference_jobs; maestro de explicaciones y
revisiones.
Qué contiene:
  Modelo, versión, hashes de artefactos, hash y fuente de entrada, lateralidad,
  probabilidades, umbral, resultado de tamiz, origen del KL, latencia,
  dispositivo, usuario, correlation ID y fecha.
Para qué se usa:
  Para conservar los resultados de CNN, XGBoost y LSTM con todos los datos
  necesarios para reproducir y auditar cada inferencia.


TABLA: gradcam_explanations
Tipo: detalle de model_predictions.
Qué contiene:
  Predicción, backbone utilizado, archivo cifrado del mapa y KL objetivo.
Para qué se usa:
  Para relacionar una clasificación KL con sus mapas visuales de ResNet50 y
  DenseNet121.


TABLA: clinician_reviews
Tipo: detalle de model_predictions.
Qué contiene:
  Predicción revisada, decisión, KL confirmado, motivo, médico revisor y fecha.
Para qué se usa:
  Para guardar la confirmación, corrección o rechazo realizado por el médico
  sin modificar el resultado original del modelo.


TABLA: draft_reports
Tipo: detalle de clinical_episodes.
Qué contiene:
  Episodio, archivo PDF cifrado, estado, tipo de reporte, usuario generador y
  fecha.
Para qué se usa:
  Para conservar las distintas versiones de reportes por episodio o
  longitudinales y permitir su descarga autenticada.


TABLA: app_settings
Tipo: maestro independiente de configuración.
Qué contiene:
  Clave de configuración, valor JSON, usuario que actualizó y fecha.
Para qué se usa:
  Para configurar datos generales sin modificar el código, como el nombre de
  la institución, subtítulo del reporte y prefijo de historia clínica.


TABLA: audit_events
Tipo: detalle histórico global.
Qué contiene:
  Actor, acción, tipo e identificador de entidad, correlation ID, metadatos y
  fecha del evento.
Para qué se usa:
  Para conocer quién realizó una operación, sobre qué registro y cuándo. Sus
  filas no pueden editarse ni eliminarse.


TABLA: schema_migrations
Tipo: tabla técnica independiente.
Qué contiene:
  Nombre de la migración y fecha en que fue aplicada.
Para qué se usa:
  Para que la aplicación sepa qué cambios de estructura ya existen en la base
  y no vuelva a ejecutarlos.
